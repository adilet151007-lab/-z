# Google-вход в отдельной бете

Подготовлен серверный Authorization Code flow. Статический хостинг не может хранить Client Secret или проверять Google-токены. До создания OAuth-клиента рабочий Google-вход включить нельзя. Этот этап не переносит результаты существующих игроков в Google-профили и не создаёт несколько комнат.

## 1. Отдельный сервер

Оставить `culture-quest-z`, `main` и рабочую базу без изменений. Для серверной беты использовать отдельный Render Web Service из ветки `beta/lobby` и отдельную PostgreSQL-базу.

- Build: `npm ci --omit=dev && npm ci --prefix beta-lobby --omit=dev && node beta-lobby/build.mjs`
- Start: `node beta-lobby/server.mjs`
- Health: `/health`
- `LOBBY_PUBLIC_ORIGIN`: точный HTTPS-домен нового сервиса, без завершающего `/`.
- `LOBBY_SESSION_SECRET`: отдельная случайная строка минимум 32 символа.
- `LOBBY_DATABASE_URL`: строка подключения **отдельной** базы. Этот entry point намеренно игнорирует `DATABASE_URL`, чтобы не подключиться к рабочей игре по унаследованной настройке.
- `TEACHER_PASSWORD`: отдельный пароль преподавателя беты.
- `SESSION_SECRET`: отдельный случайный секрет игрового движка беты, минимум 32 символа.

Сервис и база этой инструкцией не создаются. У Free Web Service нет постоянного локального диска: для сохранения класса между деплоями нужна отдельная постоянная база. Не копировать в бету рабочую строку подключения. У серверной беты изначально отдельная пустая игра; статическое лобби продолжает открывать существующую игру.

## 2. OAuth-клиент Google

1. Открыть Google Cloud Console → Google Auth Platform. Создать/выбрать проект.
2. В Branding заполнить название приложения, email поддержки, домашнюю страницу и политику конфиденциальности. Для политики беты есть `/lobby-privacy.html`.
3. В Audience выбрать подходящую аудиторию. Пока приложение в Testing, добавить тестовые Google-аккаунты. Публикацию и требования проверки Google пройти перед массовым запуском.
4. Clients → Create client → **Web application**.
5. Authorized JavaScript origins: значение `LOBBY_PUBLIC_ORIGIN`. Для этого серверного потока JavaScript SDK Google не требуется.
6. Authorized redirect URIs: **`LOBBY_PUBLIC_ORIGIN` + `/auth/google/callback`**. Домен, HTTPS и путь должны совпасть точно.
7. Сохранить выданный Client ID в `GOOGLE_CLIENT_ID`, Client Secret — в `GOOGLE_CLIENT_SECRET` в Environment **нового** Render-сервиса. Секрет не публиковать в GitHub, HTML и переписке.
8. Развернуть серверную бету. В «Войти» появится активный переход «Войти через Google».

Области доступа: `openid profile email`. Доступ к Gmail, Drive и контактам не запрашивается. Google-идентификатор не используется как пароль преподавателя и не повышает роль.

## 3. Проверка владельцем

- Войти тестовым аккаунтом Google. На странице должен появиться настоящий профиль, а после перезагрузки — восстановиться.
- Убедиться, что Google-профиль сам по себе не открывает пульт преподавателя.
- Выйти: cookie текущего браузера удаляется. Войти отменённым/повторным callback не получится.
- В пульте беты открыть вход и скопировать «Постоянную ссылку класса». Закрыть, открыть или продлить вход: скопированный адрес должен остаться прежним.
- Проверить вход по старому постоянному адресу с другого браузера. После явного отзыва ссылки старый адрес не должен регистрировать новых участников.

Локальная проверка с синтетическим Google-провайдером:

```sh
npm ci
npm ci --prefix beta-lobby
node --test beta-lobby/tests/account.test.mjs beta-lobby/tests/stable-entry.test.mjs
```

Эти десять проверок не подтверждают настройку реального Google Cloud и не заменяют контрольный вход владельца. Текущий статический сервис не становится OAuth-сервером от добавления Client ID.

Документация: https://developers.google.com/identity/openid-connect/openid-connect
