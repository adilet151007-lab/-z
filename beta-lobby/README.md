# Бета-лобби

Отдельный статический сайт со своим оформлением и хранилищем настроек браузера. Каталог содержит одну существующую игру. Кнопки ведут на штатные `student.html` и `teacher.html`; лобби само не создаёт игрока, не входит преподавателем и не обращается к API или PostgreSQL рабочей игры.

Рабочая версия зафиксирована на `bbba854f98a901e379f41c1ca208ce8cd586d11e`, ветка `main`, сервис `culture-quest-z`. Изменения первого этапа находятся только в `beta-lobby/`, ветка `beta/lobby`. Публикация беты выполняется отдельным Static Site; сервис рабочей игры не перенастраивать и не перезапускать.

## Что работает

- Каталог существующей игры и поиск по предмету/формату.
- Вход по обычной ссылке занятия преподавателя или её коду допуска; адрес и формат проверяются, подлинность и состояние входа определяет сервер игры.
- Бета-ссылка `https://<бета-домен>/#join=<код-допуска>` также передаёт приглашение штатной игре. Фрагмент убирается из адресной строки после чтения. Приглашение остаётся только в sessionStorage этой вкладки, без отправки в аналитику или HTTP-журналы лобби.
- Восстановление ранее введённого приглашения и его удаление из лобби. Удаление не отзывает допуск на сервере.
- Отдельный переход в пульт преподавателя, справка, русский/казахский язык, светлая/тёмная тема.
- На экране нет вымышленных показателей текущего онлайна, таймера или результатов. Состояние матча на этом этапе показывает сама игра.

## Сервер Google-входа без игровой базы

`node beta-lobby/portal-server.mjs` запускает отдельное лобби с Google-профилем. Оно открывает существующую игру, не подключается к её PostgreSQL и не запускает её движок. Нужны только `LOBBY_SESSION_SECRET`, `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET`. Адрес callback — домен нового сервиса + `/auth/google/callback`. Настройка описана в [GOOGLE_SETUP.md](GOOGLE_SETUP.md).

## Постоянная ссылка класса и Google

В этой ветке подготовлен серверный вариант: `node beta-lobby/server.mjs`. Он показывает лобби и существующие игровые фронтенды на одном отдельном домене, использует только `LOBBY_DATABASE_URL` (не `DATABASE_URL` рабочей игры) и подключает Google через серверный OAuth Authorization Code flow. Настройка: [GOOGLE_SETUP.md](GOOGLE_SETUP.md).

- Новая **постоянная ссылка класса** подписана сервером и связана с сохранённым идентификатором класса. Продление допуска, открытие/закрытие входа, сброс матча и перезапуск с сохранённой базой не меняют её. Закрытый вход по ссылке не пропускает новых студентов. Отдельная подтверждаемая команда «Отозвать постоянную ссылку» меняет адрес. Уже вошедших не отключает.
- Старые временные приглашения совместимы с сервером и лобби, но сохраняют прежний срок действия. Чтобы раздать один адрес на следующие занятия, преподаватель копирует **постоянную** ссылку после серверного обновления.
- Google проверяется официальной `google-auth-library`: подпись ID token, аудитория, издатель и срок действия, дополнительно nonce, state, PKCE и cookie браузера. Callback одноразовый. Имя и подтверждённый email возвращаются только собственной подписанной HttpOnly-сессии. Аккаунт не даёт прав преподавателя или администратора.
- Аккаунт хранит личность в cookie до 7 дней. Постоянная статистика и несколько независимых игровых комнат ещё не реализованы.
- В статическом предпросмотре есть окно профиля, но Google помечен как ещё не открытый. Оно не имитирует авторизацию и не делает запросов к отсутствующему API. Реальный Google-вход не проверен: OAuth-клиент владельцем ещё не создан. Проверки с синтетическим провайдером находятся в `tests/account.test.mjs`.

**На рабочем сервере эти изменения пока не опубликованы.** Его временные ссылки пока работают по прежним правилам. Обновление одной статической страницы не может изменить допуск на другом сервере. Ветка `main`, сервис рабочей игры и его база не изменяются.

## Проверка и запуск

Из корня репозитория, без установки зависимостей:

```sh
node beta-lobby/build.mjs
node --test beta-lobby/tests/core.test.mjs
python3 -m http.server 4173 --directory beta-lobby/public
```

Открыть `http://localhost:4173`. Локально можно проверить приглашение из рабочей игры; обёртка приглашения на бета-домене требует HTTPS.

## Отдельная публикация на Render

- Тип: Static Site.
- Репозиторий: `https://github.com/adilet151007-lab/-z`.
- Ветка: **beta/lobby**.
- Build Command: `node beta-lobby/build.mjs`.
- Publish Directory: **beta-lobby/public**. Корень репозитория публиковать нельзя.
- Environment: `SKIP_INSTALL_DEPS=true`.
- Секреты, DATABASE_URL и пароль преподавателя не нужны.

Публичная папка содержит ровно пятнадцать файлов; build отклоняет неожиданные файлы и внешние зависимости. CSP разрешает скриптам только свой сервер и запрещает встроенные скрипты и отправку форм. Переход к игре происходит по действию пользователя на разрешённый адрес. Служебная страница `/mobile-preview.html` показывает лобби во фрейме 390 × 844 для проверки вёрстки; она не эмулирует аппаратную производительность телефона.

При необходимости дополнительных CDN-заголовков настройте для Static Site `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Permissions-Policy: camera=(), microphone=(), geolocation=()` и политику iframe. Серверные заголовки настраиваются в сервисе отдельно; CSP в HTML не заменяет `frame-ancestors`.


## Профили и независимые комнаты

Актуальный сервер — `node beta-lobby/portal-server.mjs`. См. [PLATFORM_SETUP.md](PLATFORM_SETUP.md). На Render без отдельной `LOBBY_DATABASE_URL` постоянные профили и комнаты явно выключены. Google-вход и переходы в старую игру работают как раньше. `DATABASE_URL` основной игры не читается.
